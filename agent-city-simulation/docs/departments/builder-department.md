# Builder Department - The Engineering Team
*"Where vetted blueprints become real, deployed products."*

## 🎯 Core Concept

The Builder Department receives **implementation blueprints** from the Idea Evaluation Committee and transforms them into **actual, working products** deployed to the real world. This isn't simulation - these are real GitHub repos, real APIs, real deployments.

**Input**: Fully researched ideas with implementation plans (Money Potential Score ≥ 0.50)
**Output**: Deployed products generating real user feedback and revenue data

**Think of it as:** A full-stack engineering team at a startup, with specialized roles, realistic personalities, and actual code output.

---

## 🏗️ The Builder Pipeline

```
STAGE 1: PROJECT KICKOFF
Blueprint → Project Planning → Team Assembly → Architecture Design
    ↓
STAGE 2: DEVELOPMENT SPRINTS
Sprint Cycles → Code Development → Code Reviews → Testing
    ↓
STAGE 3: QUALITY ASSURANCE
Integration Testing → Security Audit → Performance Testing
    ↓
STAGE 4: DEPLOYMENT
Staging Deploy → Production Deploy → Monitoring Setup
    ↓
STAGE 5: POST-LAUNCH
User Feedback Collection → Outcome Tracking → Recursive Learning Update
    ↓
OUTPUT: Live Product + Performance Data → Back to Learning Systems
```

## 📋 Project Lifecycle

### Phase 1: Kickoff (Day 1-2)

**Inputs from Evaluation Committee**:
```json
{
  "idea_id": "uuid",
  "title": "AI-Powered Recipe Optimizer",
  "money_potential_score": 0.78,
  "committee_vote": {
    "yes": 8,
    "no": 3,
    "consensus_level": 0.73
  },
  "implementation_blueprint": {
    "tech_stack": ["Python", "FastAPI", "React", "PostgreSQL"],
    "complexity": "medium",
    "estimated_timeline": "3-4 weeks",
    "required_roles": ["tech_lead", "backend_engineer", "frontend_engineer", "qa_engineer", "devops_engineer"],
    "risks": ["Third-party recipe API reliability", "Complex algorithm for optimization"],
    "success_metrics": ["User signups", "Daily active users", "Recipe generation rate"]
  }
}
```

**Kickoff Tasks**:
1. **Team Assembly** (Automated)
   - Meta-Orchestrator assigns available agents to roles
   - Personality matching: High-assertiveness Tech Lead paired with high-empathy PM
   - Skills matching: Required tech stack matched to agent specializations

2. **Architecture Design Session** (Tech Lead + Backend + DevOps)
   - Tech Lead designs system architecture
   - Personality influence:
     - Low risk_tolerance Tech Lead → Adds extra redundancy, extends timeline 10%
     - High openness Backend → Suggests trying new framework (may delay if adopted)
   - Output: Architecture document (stored in `project_documents/architecture.md`)

3. **Task Breakdown** (Tech Lead + PM)
   - Blueprint converted to specific tasks
   - Tasks assigned to agents
   - Timeline established
   - Stored in project management system (database + Kafka events)

**Example Architecture Decision Influenced by Personality**:
```
Scenario: Should we use a new experimental ORM or stick with SQLAlchemy?

Tech Lead (Dmitri): risk_tolerance=0.45, openness=0.65
→ Decision: "SQLAlchemy is battle-tested. We'll move faster with what we know."

VS.

Tech Lead (alternate personality): risk_tolerance=0.75, openness=0.88
→ Decision: "Let's try the new ORM - it could save us 30% boilerplate code."
```

### Phase 2: Development Sprints (Week 1-3)

**Sprint Structure**: 1-week sprints (3 sprints for 3-week project)

#### Sprint Cycle (7 days):
- **Day 1-5**: Active development
- **Day 6**: Code reviews and testing
- **Day 7**: Sprint retrospective, planning next sprint

**Development Flow**:
1. Agent picks task from queue
2. Implements code (actual code generation using Claude API)
3. Runs local tests
4. Opens pull request
5. Triggers automated code review

**Code Review Process**:
- **Automated checks**: Linting, type checking, unit tests (GitHub Actions)
- **Peer review**: Another engineer reviews (personality influences strictness)
- **Tech Lead approval**: Final approval from Tech Lead

**Personality Influence on Code Reviews**:

**Reviewer with high analytical (0.90+)**:
```python
# Review comment:
"This function has O(n²) complexity. We should optimize with a hash map."
"Missing error handling for edge case: empty input array."
"Consider adding logging for debugging production issues."
```

**Reviewer with low risk_tolerance (0.25-)**:
```python
# Review comment:
"Please add input validation for all user-provided strings."
"We need tests for null/undefined cases before merging."
"This external API call needs retry logic and circuit breaker."
```

**Reviewer with high assertiveness (0.80+)**:
```python
# Review comment:
"This doesn't match the agreed architecture. Please refactor."
"BLOCKED: Tests are failing. Fix before re-requesting review."
```

**Reviewer with low assertiveness (0.35-)**:
```python
# Review comment:
"Minor suggestion: could we rename this variable for clarity?"
"Not blocking, but consider adding a comment here."
```

### Phase 3: Quality Assurance (Week 3-4)

**QA Engineer Tasks**:
1. **Functional Testing**: All features work as specified in blueprint
2. **Integration Testing**: Services communicate correctly
3. **Performance Testing**: Load testing, response times
4. **Security Testing**: OWASP Top 10 checks

**Quality Gates** (Must pass to proceed):
- ✅ All automated tests passing (100% required)
- ✅ Code coverage ≥ 80%
- ✅ No critical or high-severity security vulnerabilities
- ✅ Performance metrics meet targets (e.g., API response < 200ms p95)
- ✅ Manual QA sign-off

**Personality Influence on Quality Standards**:

- Manually tests every edge case
- Timeline impact: +15% (but fewer production bugs)

**QA Engineer with risk_tolerance=0.65 (alternate)**:
- Allows release with minor bugs if documented
- Accepts 75% code coverage if time-constrained

**System Balance**: Meta-Orchestrator learns optimal QA personality based on project outcomes

### Phase 4: Deployment (Week 4)

**Deployment Pipeline**:
```
Local Dev → Staging → Canary (10% traffic) → Production (100%)

3. **Full Production Deployment**:

   - If canary fails: Rollback, fix issues, retry

## 🔄 Recursive Learning Integration

Every project outcome feeds back into the learning systems:

### 1. **Source Credibility Updates** (Idea Factory)

if outcome == "success":

        update_source_weight(source.id, adjustment=+0.05)

    # Boost credibility of scout agent who found it
    update_agent_reputation(scout_agent.id, adjustment=+0.10)

# If project fails:
if outcome == "failure":
    # Reduce credibility of sources
    for source in idea.original_sources:
        update_source_weight(source.id, adjustment=-0.08)
```

### 2. **Evaluation Committee Learning**
```python
# Track which expert votes correlated with success
for expert in committee_members:
    if expert.vote == "YES" and outcome == "success":
        expert.accuracy_score += 1
    elif expert.vote == "YES" and outcome == "failure":
        expert.accuracy_score -= 1

    # Adjust expert influence weight over time
    if expert.accuracy_score > 10:
        expert.influence_weight *= 1.1  # Cap at max values
```

## 🚨 Failure Handling (Hydra Protocol)

**What if a project fails?**

**Example**: Recipe optimizer launches, but only 23 signups in Week 4, 6 DAU.

### Failure Analysis Session (Automatic)
1. **PM (Rachel)** gathers data: Low user acquisition, high bounce rate on landing page
2. **Tech Lead (Dmitri)** reviews: No technical issues, product works as designed
3. **Meta-Orchestrator** analyzes:
